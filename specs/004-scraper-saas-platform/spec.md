# Feature Specification: 全栈爬虫 SaaS 平台

**Feature Branch**: `004-scraper-saas-platform`
**Created**: 2025-12-18
**Status**: Draft
**Input**: 全栈爬虫 SaaS 平台需求规格书 - 多渠道采集、多租户系统、配额管理、安全鉴权、数据治理、HUD Dashboard、可观测性监控
**Constitution**: v3.0.0 (Reference: `.specify/memory/constitution.md`)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用户注册与安全登录 (Priority: P1)

作为一个新用户，我希望能够通过邮箱注册账户并使用滑块验证码完成安全登录，以便开始使用爬虫平台的功能。

**Why this priority**: 用户认证是所有 SaaS 功能的基础门槛，没有安全的身份验证系统，其他所有功能都无法安全使用。滑块验证码防止机器人批量注册和暴力破解。

**Independent Test**: 可以通过注册新账户、完成滑块验证、登录系统来完整测试，成功后用户能看到个人 Dashboard。

**Acceptance Scenarios**:

1. **Given** 用户访问注册页面, **When** 填写邮箱、密码并完成滑块验证码, **Then** 系统发送验证邮件，用户收到确认链接
2. **Given** 用户已注册且邮箱已验证, **When** 在登录页输入正确凭证并完成滑块验证码, **Then** 成功登录并跳转至个人 Dashboard
3. **Given** 用户连续3次滑块验证失败, **When** 再次尝试验证, **Then** 系统显示冷却倒计时（60秒）后才能重试
4. **Given** 用户登录状态, **When** 超过2小时无操作, **Then** 系统自动登出并提示重新登录

---

### User Story 2 - 新闻站点内容采集 (Priority: P1)

作为一个普通用户，我希望能够配置并运行新闻站点爬虫任务，自动采集指定网站的新闻内容（标题、正文、元数据），以便进行后续的数据分析。

**Why this priority**: 新闻采集是平台的核心价值功能，用户注册的主要目的就是采集数据。支持主流新闻站点的正文提取是基础能力。

**Independent Test**: 可以通过创建一个新闻采集任务、运行采集、查看采集结果来完整测试，用户能看到结构化的新闻数据。

**Acceptance Scenarios**:

1. **Given** 用户已登录, **When** 在"新建任务"页面选择"新闻站点"类型并输入目标URL, **Then** 系统验证URL有效性并显示预览信息
2. **Given** 用户配置好采集任务, **When** 点击"立即运行", **Then** 系统开始采集并实时显示进度（已采集/待采集/失败数）
3. **Given** 采集任务完成, **When** 用户查看结果列表, **Then** 显示提取的标题、摘要、发布时间、来源等结构化字段
4. **Given** 采集内容与已存在内容重复, **When** 系统执行去重检查, **Then** 自动跳过重复内容并标记"去重跳过"

---

### User Story 3 - 社交媒体会话流采集 (Priority: P2)

作为一个高级用户，我希望能够采集 Twitter/X 和 Telegram 的会话流（Thread/Session），保持消息的时间线和回复关系，以便分析社交舆情。

**Why this priority**: 社交媒体采集需要特殊的会话结构处理，复杂度高于新闻站点，但对于舆情分析场景价值很高。

**Independent Test**: 可以通过配置 Twitter Thread 或 Telegram 频道采集任务、运行采集、查看会话结构来完整测试。

**Acceptance Scenarios**:

1. **Given** 用户选择"社交媒体"采集类型, **When** 输入 Twitter Thread URL, **Then** 系统识别为会话流类型并显示预估消息数量
2. **Given** Twitter Thread 采集完成, **When** 用户查看结果, **Then** 消息按时间线排列，回复关系以树形结构展示
3. **Given** Telegram 频道采集任务运行中, **When** 频道有新消息发布, **Then** 系统增量采集新消息并合并到已有会话流
4. **Given** 社交媒体消息包含引用/转发, **When** 系统解析消息, **Then** 保留原始引用关系和来源用户信息

---

### User Story 4 - 多租户数据隔离与权限管理 (Priority: P2)

作为一个管理员，我希望能够管理多个租户（用户组），确保每个租户只能看到自己的数据，同时我作为超级管理员可以查看所有租户的数据。

**Why this priority**: 多租户是 SaaS 商业模式的基础，数据隔离涉及安全合规，必须在早期确保正确实现。

**Independent Test**: 可以通过创建多个租户用户、各自运行采集任务、验证数据隔离、超级管理员查看全部数据来完整测试。

**Acceptance Scenarios**:

1. **Given** 管理员在用户管理页面, **When** 创建新用户并分配到租户A, **Then** 该用户登录后只能看到租户A的数据
2. **Given** 租户A和租户B各自运行采集任务, **When** 租户A用户查看任务列表, **Then** 只显示租户A的任务，租户B的任务不可见
3. **Given** 超级管理员登录系统, **When** 访问"全局数据"面板, **Then** 可以查看和筛选所有租户的数据
4. **Given** 普通用户尝试访问其他租户的数据URL, **When** 系统处理请求, **Then** 返回403权限拒绝错误

---

### User Story 5 - 配额管理与使用量控制 (Priority: P2)

作为一个平台运营者，我希望能够为不同等级的用户设置每日采集配额和并发任务限制，防止资源滥用。

**Why this priority**: 配额管理是 SaaS 变现的基础，也是保护平台资源的必要措施，需要在多用户场景前实现。

**Independent Test**: 可以通过设置用户配额、用户运行任务直到达到配额、验证限制生效来完整测试。

**Acceptance Scenarios**:

1. **Given** 管理员为"基础版"用户设置每日100条采集配额, **When** 基础版用户当日采集达到100条, **Then** 后续采集请求被拒绝并显示"配额已用尽，明日重置"
2. **Given** 用户当前有3个任务并行运行（达到并发上限）, **When** 尝试启动第4个任务, **Then** 系统提示"并发任务数已达上限，请等待现有任务完成"
3. **Given** 用户配额即将用尽（剩余10%）, **When** 用户登录Dashboard, **Then** 显示醒目的配额警告提示
4. **Given** 每日UTC 0点, **When** 系统执行配额重置, **Then** 所有用户的每日配额恢复至初始值

---

### User Story 6 - HUD 风格实时监控 Dashboard (Priority: P3)

作为一个用户，我希望在 Dashboard 上看到科幻电影 HUD 风格的实时监控面板，展示系统状态、采集统计、资源使用情况。

**Why this priority**: Dashboard 是用户日常使用的主界面，良好的可视化体验提升用户满意度，但不阻塞核心功能。

**Independent Test**: 可以通过登录后查看 Dashboard、观察数据实时更新、验证图表交互来完整测试。

**Acceptance Scenarios**:

1. **Given** 用户登录后进入Dashboard, **When** 页面加载完成, **Then** 显示采集统计卡片（今日采集数、成功率、活跃任务数）
2. **Given** Dashboard 已加载, **When** 有新的采集数据产生, **Then** 统计数字实时更新（无需刷新页面）
3. **Given** 用户查看"采集趋势"图表, **When** 鼠标悬浮在数据点上, **Then** 显示该时间点的详细数据（采集数、去重数、失败数）
4. **Given** Dashboard 处于激活状态, **When** 系统检测到异常（任务失败率>20%）, **Then** 相关卡片边框变为警告色并显示异常提示

---

### User Story 7 - 全文检索与数据导出 (Priority: P3)

作为一个用户，我希望能够对采集的内容进行全文检索，并将结果导出为常用格式。

**Why this priority**: 检索和导出是数据利用的关键环节，增强平台的实用价值。

**Independent Test**: 可以通过输入关键词搜索、验证结果准确性、导出数据文件来完整测试。

**Acceptance Scenarios**:

1. **Given** 用户在搜索框输入关键词, **When** 点击搜索, **Then** 系统在1秒内返回匹配结果，关键词高亮显示
2. **Given** 搜索结果超过100条, **When** 用户滚动列表, **Then** 系统自动加载更多结果（无限滚动）
3. **Given** 用户选中多条搜索结果, **When** 点击"导出"并选择格式（CSV/JSON/Excel）, **Then** 系统生成文件并提供下载链接
4. **Given** 用户搜索无结果, **When** 页面显示空状态, **Then** 提供搜索建议（如"尝试更宽泛的关键词"）

---

### User Story 8 - 运维监控与审计日志 (Priority: P3)

作为一个系统管理员，我希望能够监控系统资源使用情况并查看操作审计日志，以便排查问题和安全审计。

**Why this priority**: 可观测性是生产环境运维的必要能力，但可以在核心功能稳定后完善。

**Independent Test**: 可以通过查看系统监控面板、执行敏感操作后验证审计日志记录来完整测试。

**Acceptance Scenarios**:

1. **Given** 管理员访问"系统监控"页面, **When** 页面加载完成, **Then** 显示实时资源指标（任务队列长度、处理速率）
2. **Given** 任务队列积压超过阈值（100个待处理）, **When** 系统检测到积压, **Then** 触发告警通知并在监控面板高亮显示
3. **Given** 任意用户执行敏感操作（删除数据、修改配置）, **When** 操作完成, **Then** 审计日志记录操作者、操作类型、时间、来源IP
4. **Given** 管理员查看审计日志, **When** 按时间范围和操作类型筛选, **Then** 显示符合条件的日志列表，支持导出

---

### Edge Cases

- 当用户网络不稳定导致滑块验证码加载失败时，系统显示重试按钮和替代验证方式（图形验证码）
- 当采集目标网站返回 403/429 错误时，系统自动暂停该任务并通知用户，不消耗配额
- 当用户的会话Token过期但正在进行长时间采集任务时，任务继续执行但用户需重新登录才能查看结果
- 当全文检索服务不可用时，系统降级为数据库模糊搜索并提示用户"搜索功能受限"
- 当同一租户的多个用户同时达到配额限制时，系统按请求时间顺序处理，公平分配剩余配额
- 当 Twitter/Telegram 会话流过长（超过1000条消息）时，系统分批采集并提供进度提示

## Requirements *(mandatory)*

### Functional Requirements

**用户与认证**
- **FR-001**: 系统 MUST 支持邮箱+密码的用户注册流程
- **FR-002**: 系统 MUST 在登录和注册流程中集成滑块验证码（Slider Captcha），适配深色主题
- **FR-003**: 系统 MUST 在滑块验证连续失败3次后触发60秒冷却期
- **FR-004**: 系统 MUST 在用户2小时无操作后自动登出会话
- **FR-005**: 系统 MUST 发送邮箱验证链接，用户点击后激活账户

**多租户与权限**
- **FR-006**: 系统 MUST 支持多租户数据隔离，租户间数据完全不可见
- **FR-007**: 系统 MUST 支持三级权限角色：超级管理员、租户管理员、普通用户
- **FR-008**: 超级管理员 MUST 能够查看和管理所有租户的数据
- **FR-009**: 普通用户 MUST 只能访问自己所属租户的数据

**配额管理**
- **FR-010**: 系统 MUST 支持按用户等级设置每日采集条数配额
- **FR-011**: 系统 MUST 支持按用户等级设置最大并发任务数
- **FR-012**: 系统 MUST 在配额用尽时拒绝新的采集请求并显示明确提示
- **FR-013**: 系统 MUST 每日 UTC 0:00 自动重置用户配额
- **FR-014**: 系统 MUST 在用户配额剩余10%时显示警告提示

**数据采集 - 新闻站点**
- **FR-015**: 系统 MUST 支持从新闻站点提取正文、标题、发布时间、作者、来源等元数据
- **FR-016**: 系统 MUST 对采集内容进行去重处理（基于 URL 和内容相似度）
- **FR-017**: 系统 MUST 在采集过程中实时显示进度（已采集/待采集/失败数）

**数据采集 - 社交媒体**
- **FR-018**: 系统 MUST 支持采集 Twitter/X Thread 的完整会话流
- **FR-019**: 系统 MUST 支持采集 Telegram 频道/群组的消息
- **FR-020**: 社交媒体数据 MUST 保持消息时间线顺序和回复/引用关系
- **FR-021**: 系统 MUST 支持 Telegram 频道的增量采集（只采集新消息）

**数据治理**
- **FR-022**: 系统 MUST 对所有采集内容提供全文检索能力
- **FR-023**: 全文检索 MUST 在1秒内返回结果（1000条以内）
- **FR-024**: 系统 MUST 支持将数据导出为 CSV、JSON、Excel 格式
- **FR-025**: 系统 MUST 使用 URL Hash + SimHash 双重机制进行内容去重

**Dashboard 与监控**
- **FR-026**: Dashboard MUST 实时展示采集统计（今日采集数、成功率、活跃任务数）
- **FR-027**: Dashboard 数据 MUST 通过实时推送更新，无需手动刷新
- **FR-028**: 系统 MUST 在异常情况（失败率>20%）时在 Dashboard 显示警告

**运维与审计**
- **FR-029**: 系统 MUST 实时监控任务队列状态（队列长度、处理速率）
- **FR-030**: 系统 MUST 在队列积压超过阈值时触发告警
- **FR-031**: 系统 MUST 记录所有敏感操作的审计日志（操作者、类型、时间、IP）
- **FR-032**: 审计日志 MUST 支持按时间和操作类型筛选、导出

### Key Entities

- **User (用户)**: 系统使用者，包含邮箱、密码哈希、所属租户、角色、配额等级等属性
- **Tenant (租户)**: 用户组/组织，用于数据隔离，包含租户名称、配额配置、创建时间等
- **ScrapingTask (采集任务)**: 用户创建的采集作业，包含任务类型（新闻/社交）、目标URL、状态、配置参数等
- **NewsArticle (新闻文章)**: 从新闻站点采集的结构化内容，包含标题、正文、来源、发布时间、URL哈希、内容指纹等
- **SocialSession (社交会话)**: Twitter Thread 或 Telegram 对话的会话容器，包含会话ID、平台类型、起始消息等
- **SocialMessage (社交消息)**: 单条社交媒体消息，包含内容、发送者、时间、父消息ID（回复关系）、引用信息等
- **Quota (配额)**: 用户配额配置与使用记录，包含每日限额、并发限额、已使用量、重置时间等
- **AuditLog (审计日志)**: 敏感操作记录，包含操作者、操作类型、目标资源、来源IP、时间戳等

## Success Criteria *(mandatory)*

### Measurable Outcomes

**用户体验**
- **SC-001**: 用户完成注册流程（含邮箱验证）平均耗时不超过3分钟
- **SC-002**: 滑块验证码加载时间不超过2秒，95%的用户能在首次尝试内完成验证
- **SC-003**: 用户从登录到看到 Dashboard 数据的时间不超过3秒

**数据采集**
- **SC-004**: 新闻站点正文提取准确率达到95%以上（标题、正文、时间完整）
- **SC-005**: 社交媒体会话流完整性达到99%（消息无丢失、顺序正确）
- **SC-006**: 单个采集任务（100条内容）完成时间不超过60秒
- **SC-007**: 内容去重准确率达到98%（误判率<2%）

**系统性能**
- **SC-008**: 系统支持1000个并发活跃采集任务而不出现明显性能下降
- **SC-009**: 全文检索在10万条数据量下响应时间不超过1秒
- **SC-010**: Dashboard 实时数据更新延迟不超过2秒

**安全与合规**
- **SC-011**: 租户数据隔离100%有效（任何情况下无法跨租户访问数据）
- **SC-012**: 所有敏感操作100%记录审计日志
- **SC-013**: 滑块验证码能够阻止99%的自动化攻击尝试

**业务指标**
- **SC-014**: 用户配额提示清晰，90%的用户能够理解自己的配额使用情况
- **SC-015**: 系统异常告警准确率达到95%（减少误报）

## Assumptions

- 用户使用现代浏览器（Chrome/Firefox/Safari/Edge 最近2个主要版本）
- Twitter/X 和 Telegram 的采集通过官方或第三方授权API进行，非未授权爬取
- 邮箱验证服务使用第三方邮件服务（如 SendGrid、AWS SES）
- 初始版本支持中文和英文界面
- 配额等级在初始版本分为：免费版（100条/日）、基础版（1000条/日）、专业版（10000条/日）
- 系统部署在云环境，具备弹性扩展能力
